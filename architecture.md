# Mario Kart World Screen Reader - Architecture & Implementation Spec

## 1. Project Goal & Scope

The core objective is to build a human-in-the-loop data pipeline to rapidly classify and label video frames from *Mario Kart World* gameplay. This labeled data will subsequently be used to train an offline machine learning model that extracts game state information (placement, laps, coins, items) from a video stream.

**Important:** This tool is strictly an **offline pipeline**. It does not run real-time inference during gameplay. The workflow is:

1. **Record & Trim:** Capture gameplay from the Nintendo Switch 2 (via HDMI capture card) and trim to the exact race duration.
2. **Preprocess:** Run the Python script with metadata flags. This extracts frames into a dedicated folder and initializes a `data.csv`.
3. **Classify:** Start the web-based Classifier (`pnpm start`). It uses software heuristics to "guess" labels for human verification.
4. **Train:** Export the finalized labels to train the PyTorch ML models.
5. **Deploy:** Use the trained models in real-time applications (Coach, Commentator, etc.).

## 2. Exhaustive Technology Stack

The project utilizes a flat monorepo structure. The modules do not share package managers; they communicate purely via a shared Protocol Buffer (`.proto`) schema and the local filesystem.

### 2.1 Shared Data (`/data`)

* **Protobufs:** Shared schemas for enums (Placement, LapCount, etc.) and Guess formats.
* **JS/TS Generator:** `@bufbuild/protoc-gen-es`.
* **Purpose:** Ensures the Express backend and Next.js frontend use identical types. **It is not used for on-disk frame data storage.**

### 2.2 Preprocessor (`/preprocessor`)

* **Runtime:** Python 3.10+ (PyTorch for future active learning).
* **Flags:** `--video`, `--name`, `--time`, etc.
* **Output:** Creates a folder named after the video file containing frames and a `data.csv`.
* **Env:** Uses `.env` for `DATA_DIR`.

### 2.3 Classifier (`/classifier`)

* **Backend:** Express.js (started via `pnpm start`). Handles folder discovery and heuristic logic.
* **Frontend:** Next.js (Static Export). Provides a premium, dark-mode labeling interface.
* **State Management:** Simple React state; the backend is the source of truth for the CSV.

## 3. Storage: The CSV Frame Data Structure

The source of truth for the classification data is a simple CSV file generated by the Python preprocessor and continuously updated by the Node.js backend.

### 3.1 Naming Convention (The Run ID)

Every race run is assigned a unique ID used for the video file, the frame folder, and the dataset CSV. The ID is composed of the following parts connected by underscores:

1. `mkw`: Project prefix.
2. `track_name`: Shortened track name (e.g., `royal_ruins`).
3. `p[N]`: Number of players (e.g., `p1`, `p2`).
4. `type`: Race type (`standard`, `knockout`, `time_trial`).
5. `lobby`: `online` or `local`.
6. `nochat`: Gamechat mode (currently only `nochat`).
7. `date`: UTC Date in `mm_dd_yyyy`.
8. `time`: UTC Time in `hh_mm_ss` (24h).

**Example ID:** `mkw_royal_ruins_p2_standard_online_nochat_10_09_2026_06_22_34`

### 3.2 File Organization

* **Video:** `[ID].mp4` (Recorded at 1080p, trimmed to race duration).
* **Folder:** A directory named `[ID]/` containing all frames and data.
* **Frames:** `[6-digit-index]_[ID].png` (Downsampled to 960x540 for storage/ML efficiency).
* **CSV:** `UNFINISHED_[ID].csv` while in progress; prefix is stripped when 100% complete.
* **Env:** Root `.env` defines `BASE_DATA_DIR`. All tools reference this path.

### 3.3 CSV Columns

The Python script initializes the CSV with the following headers. The `frame_id` and `track` are pre-filled; the rest are left blank for the Classifier to fill out.

| Column | Example Value | Description |
| --- | --- | --- |
| `frame_id` | `000001_mkw_royal_ruins...png` | The explicit filename of the frame. |
| `track` | `royal_ruins` | Pre-filled track name. |
| `placement` | `1` | 1-24 (or blank). |
| `lap_count` | `2` | 1-7 (or blank). |
| `coin_count` | `10` | 0-20 (or blank). |
| `primary_item` | `green_shell` | The active item held. |
| `secondary_item` | `banana` | The reserved item. |
| `race_phase` | `racing` | `loading`, `countdown`, `racing`, `finished`. |

## 4. Shared Types: The Protobuf Data Contract

Protocol Buffers are used to define the exact shape of the API response so that both the backend and frontend agree on the "Guess" format and confidence levels.

---

The backend determines the "Confidence" level dynamically when a frame is requested. Confidence and guesses are **not** stored in the CSV; they are transient structs determined at runtime. If a value is in the CSV, it is treated as `CERTAIN`.

### 5.1 Heuristic Strategies

| Strategy | Target Fields | Threshold | Logic |
| --- | --- | --- | --- |
| **Binary Search** | `lap_count`, `race_phase` | N/A | Find transition frames for 3-6 lap tracks. Fills gaps once transitions are locked. |
| **Temporal Propagation** | `placement`, `coin_count` | 300 frames | Scans ±300 frames for a label. If found, suggests it as `UNCERTAIN`. |
| **Global Constant** | `track` | Infinite | Once known, propagates 100% `CERTAIN` across all frames. |

### 5.2 Dependency Injection (DI)

The frame picker and guessers are dependency-injected. This allows swapping the current software heuristics for **Active Learning** (inference-based picking) in the future by simply injecting a model-driven guesser class.

## 6. Frontend: User Experience & Design

The frontend is a **Next.js Static Export** application designed for high-speed labeling.

### 6.1 UI Principles

* **Visual Cues:** Borders change color based on confidence (Green/Yellow/Red).
* **Keyboard First:** Labels can be selected via hotkeys (e.g., 1-24 for placement).
* **Aesthetics:** Dark mode, glassmorphism, and smooth transitions between frames to reduce eye fatigue during long labeling sessions.

### 6.2 Deployment

* **Output:** `next export` produces a static folder.
* **Hosting:** GitHub Pages or S3.
* **Fallbacks:** S3/CloudFront configured to redirect 404s to `index.html`.
